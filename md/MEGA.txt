## Vision

Intuition is a deterministic perceptual training system built around stable gameplay geometry, profile-driven runtime state, and explicit ownership semantics.

The project intentionally avoids runtime chaos:

* no implicit gameplay generation,
* no hidden orchestration,
* no scattered runtime ownership,
* no renderer-driven geometry invention,
* no duplicated state synchronization.

The architecture prioritizes:

* deterministic behavior,
* stable geometry,
* explicit aggregate ownership,
* persistence consistency,
* reactive synchronization,
* append-only visual evolution,
* runtime transparency.

---

# Core Architectural Principles

## Deterministic Runtime

Runtime behavior must remain deterministic.

The same:

* profile,
* level,
* topology family,
* topology,
* renderer,
* mode,

must always produce the same gameplay geometry and gameplay behavior.

The runtime intentionally avoids:

* random layout generation,
* unstable geometry,
* hidden runtime derivation,
* non-repeatable gameplay structures.

---

## Explicit Ownership

Every mutable runtime concern must have a single canonical owner.

Ownership must never become implicitly shared between:

* ViewModels,
* repositories,
* sessions,
* renderers,
* UI state,
* persistence.

Ambiguous ownership is treated as architectural risk.

---

## Stable Geometry

Gameplay geometry is canonical domain data.

Geometry is not:

* renderer-owned,
* UI-generated,
* session-generated,
* runtime-randomized.

Geometry exists independently from rendering implementation.

---

## Aggregate Consistency

Aggregates must remain internally valid.

Cross-field invariants must be preserved atomically.

The architecture intentionally avoids:

* partially synchronized aggregates,
* runtime patching,
* UI-driven consistency repair,
* manual synchronization discipline.

---

## Reactive Synchronization

Reactive flows are the canonical runtime synchronization mechanism.

Room Flow streams propagate runtime state changes through repositories into ViewModels and UI.

Reactive synchronization is preferred over:

* manual refresh,
* imperative synchronization,
* mutable shared runtime caches.

---

# Runtime Architecture

## Profile

Profile is the primary gameplay identity aggregate.

A profile owns:

* gameplay progression,
* current level,
* gameplay mode,
* renderer selection,
* mask selection,
* topology family,
* active topology,
* notebook selection,
* activity state,
* profile type semantics.

Gameplay sessions are always created from the currently active profile snapshot.

---

## Session

Session is a temporary gameplay runtime aggregate.

A session:

* does not own topology catalogs,
* does not derive gameplay geometry,
* does not resolve topology families,
* does not generate layouts,
* does not invent button placement.

Instead, session receives a resolved gameplay snapshot from the active profile.

Session is intentionally lightweight.

---

## Round

Round is a transient gameplay execution unit.

Round operates on already resolved runtime state.

Round never:

* resolves topology,
* loads topology catalogs,
* derives geometry,
* chooses renderer layout semantics.

---

# Gameplay Geometry Architecture

## Topology

Topology is the canonical gameplay geometry source.

Topology defines:

* occupancy layout,
* cell coordinates,
* spatial structure,
* projection behavior,
* renderer geometry,
* occupancy capacity.

Topology exists independently from:

* profiles,
* sessions,
* rounds,
* renderers,
* gameplay modes.

Topology is a reusable geometry definition.

---

## Topology Cells

TopologyCell defines a concrete spatial occupancy slot.

Cells contain:

* coordinates,
* dimensions,
* blocking state,
* index order.

Cells are immutable geometry descriptors.

---

## Topology Projection

TopologyProjection defines topology rendering semantics.

Projection controls:

* alignment,
* scaling behavior,
* renderer projection semantics.

Projection does not generate geometry.

Projection interprets existing geometry.

---

## Topology Family

TopologyFamily defines a constrained topology evolution space.

Families group topology variants that belong to the same gameplay geometry progression line.

Topology families preserve stable visual semantics across level transitions.

---

# Topology Selection Model

Profiles persist:

* topologyFamilyId,
* activeTopologyCode,
* currentLevel.

The active topology is not arbitrary.

Active topology is deterministically synchronized with:

* topology family,
* current level.

Topology selection is deterministic.

---

# Topology Invariant

The following invariant must always hold:

```text id="arch_a1"
activeTopology.occupancyCapacity == currentLevel
```

Any level transition must automatically update active topology selection.

---

# Level Transition Architecture

Level transitions are aggregate mutations.

Changing profile level must atomically:

1. update currentLevel,
2. resolve matching topology inside topology family,
3. update activeTopologyCode.

Topology synchronization is persistence-driven.

The architecture intentionally avoids:

* runtime topology patching,
* ViewModel synchronization logic,
* UI-driven topology repair.

---

# Geometry Semantics

Topology codes are semantic geometry identifiers.

Examples:

* `2_0`
* `2_1`
* `2_2_1`

Topology codes are not synthetic numeric identifiers.

Codes represent stable geometry signatures.

Example:

```text id="arch_a2"
2_2_1
=
2 buttons in row 1
2 buttons in row 2
1 button in row 3
```

# Renderer Architecture

Renderer consumes topology geometry directly.

Renderer does not:

* derive geometry,
* invent layouts,
* generate coordinates,
* reinterpret occupancy structure.

Topology is the single source of truth for:

* button coordinates,
* layout structure,
* occupancy semantics,
* projection behavior,
* gameplay geometry.

Renderer is intentionally geometry-dependent rather than geometry-owning.

# Historical Context

## Reducer Collapse

Approximately two sprints ago it became clear that:

```text
BEFORE gameplay semantics did not actually exist.
```

The reducer/runtime layer emulated BEFORE execution and silently corrupted:
- runtime semantics,
- behavioral statistics,
- gameplay truthfulness.

This problem was discovered during:
- relational consistency work,
- foreign key stabilization,
- runtime ownership cleanup.

---

## First Migration Failure

An attempt to migrate toward a formal IBM/UML-like orchestration runtime failed.

Failure causes:
- implicit relationship explosion,
- orchestration complexity explosion,
- unreadable runtime graph,
- lifecycle coupling,
- supportability collapse.

The orchestrator branch was frozen.

---

## Current Runtime Direction

The project migrated toward a significantly simpler runtime architecture:

```text
GameViewModel
    ↕
Runtime Router
    ↕
Semantic Runtime Handlers
```

Current runtime principles:
- router owns transition publishing,
- handlers own business logic,
- runtime semantics are explicit,
- reducer-style orchestration removed,
- BEFORE mode now exists as real gameplay semantics.

# Overview

Statistics is a read-only observational analytics subsystem built on top of persisted deterministic gameplay runtime records.

The subsystem is intentionally designed around:

* explainable analytics
* deterministic reconstruction
* bounded interpretation
* supportability-first architecture
* trust-oriented UX
* compression-aware rendering
* runtime-independent observation

Statistics architecture intentionally remains isolated from:

* gameplay continuation
* runtime orchestration
* reducers
* routers
* renderers
* profile lifecycle
* monetization logic

Statistics MUST NEVER influence gameplay runtime behavior.

---

# 🧠 Core Principle

Statistics is now formally defined as:

```text
deterministic runtime reconstruction layer
```

instead of:

```text
UI-driven analytics projection
```

The subsystem intentionally reconstructs behavioral interpretation from persisted runtime records.

Flow remains strictly one-directional:

```text
DB
→ DAO
→ Repository
→ Engine
→ Pipeline
→ Insight
→ ViewModel
→ UI
```

Statistics:

* never modifies gameplay runtime
* never owns runtime continuation
* never generates gameplay events
* never coordinates lifecycle
* never affects outcomes

---

# ⚠️ Historical Clarification

Prior to Sprint 15:

* gameplay runtime itself contained semantic inconsistencies,
* especially around `BEFORE` mode behavior.

This affected analytics validity because:

* runtime labels claimed support for BEFORE,
* while gameplay behavior remained AFTER-only internally.

As of 0.16:

```text
statistics now observes actual deterministic runtime behavior
```

instead of observing partially synthesized reducer semantics.

This significantly improves:

* behavioral validity
* explainability
* trustworthiness
* legal/product safety

---

# 📦 Data Sources

Statistics derives everything from persisted deterministic runtime records.

Primary sources:

* sessions
* observed rounds
* runtime timing data
* round lifecycle timestamps
* gameplay mode/runtime semantics

No gameplay analytics are synthesized from UI state.

---

# Statistics Philosophy

Statistics intentionally prioritizes:

* interpretation over scoring
* explainability over opacity
* trust over manipulation
* bounded analytics over adaptive AI
* behavioral context over gamification

The subsystem intentionally avoids:

* hidden ranking systems
* opaque confidence scoring
* adaptive gameplay feedback loops
* predictive manipulation systems
* engagement optimization mechanics

# 📊 Statistics Runtime Relationship

Gameplay runtime and statistics are now explicitly separated.

Gameplay owns:

```text
runtime truth
```

Statistics owns:

```text
runtime interpretation
```

Statistics MUST NEVER:

* continue gameplay lifecycle

* false trends
* visual distortion
